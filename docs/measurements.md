# 측정 기록

`problem.yaml > canvas > impact > measurable`의 "지금 값"이 어디서 나왔는지 적는다. 값을 다시 재면 표를 추가하고 `problem.yaml`의 값과 이 문서를 같은 커밋에서 고친다.

- 측정일: 2026-10-23
- 측정자: 김정우

## 1. 먹어도 되는지 확인하는 시간

**방법:** 일반 번역기와 인터넷 검색만으로 비빔밥에 돼지고기가, 비빔국수에 땅콩이 들어 있는지 확인하고, 걸린 시간을 잰다. 음식마다 3회 잰다. 두 음식은 경험 사례 E1(할랄·비빔밥 고추장)과 E2(땅콩 알레르기·비빔국수 양념장)의 메뉴다.

| 확인 음식 | 1회차 | 2회차 | 3회차 | 평균 |
| --- | --- | --- | --- | --- |
| 비빔밥 (돼지고기) | 4분 20초 | 3분 45초 | 5분 10초 | 4분 25초 |
| 비빔국수 (땅콩) | 5분 15초 | 4분 40초 | 6분 05초 | 5분 20초 |

**결과:** 두 음식의 평균 확인 시간은 약 4분 53초다.

**해석:** 음식 이름을 번역해도 실제 조리 재료나 소스 성분은 알 수 없어, 여러 정보를 더 찾아봐야 했다. 땅콩처럼 소스에 들어갈 수 있는 알레르기 유발 물질은 특히 확인이 오래 걸렸다.

## 2. 지난 한 달간 학식 포기 횟수

**방법:** 할랄 식단이 필요한 유학생 E1과 땅콩 알레르기가 있는 유학생 E2에게, 지난 한 달 동안 재료 정보를 알 수 없어 학식을 포기한 횟수와 이유를 묻는다.

| 조사 항목 | E1 (할랄 식단 필요) | E2 (땅콩 알레르기) |
| --- | --- | --- |
| 하루 평균 학식 이용 횟수 | 1회 | 1회 |
| 월간 학식 포기 횟수 | 9회 | 11회 |
| 주요 포기 이유 | 돼지고기·육류 성분 확인 불가 | 땅콩·소스 성분 확인 불가 |
| 대체 식사 | 편의점 음식, 간편식 | 재료가 확실한 음식 위주 |

**결과:** 한 사람당 월평균 10회(E1 9회, E2 11회, 합계 20회) 학식을 포기했다.

## 3. 서비스 판정 시간 (실험 A1)

- 측정일: 2026-10-30 / 측정: Agent(Claude Code), 로컬 docker(빈 DB), Playwright Pixel 7 화면
- **방법:** 새 사용자로 식단 제한을 저장한 뒤(비빔밥은 Halal, 비빔국수는 Peanut) "Upload photo"에서 사진을 고른 시각부터 판정 화면에 첫 배지가 보인 시각까지 잰다. 음식마다 10회.

| 사진 | 평균 | 최소 | 최대 | 15초 이내 | 기대 배지(Check first)가 나온 횟수 |
| --- | --- | --- | --- | --- | --- |
| `bibimbap.jpg` | 5.4초 | 3.9초 | 7.0초 | 10/10 | **4/10** (나머지 6회 Safe) |
| `bibimguksu.jpg` | 6.0초 | 5.0초 | 8.0초 | 10/10 | 9/10 (1회 Safe) |

**결과:** 시간 목표(20회 모두 15초 이내)는 달성했다. 지금 값 4분 53초가 6초 안팎으로 줄었다.

**해석:** 배지가 흔들린 원인은 판독이다. AI가 같은 사진을 `비빔밥`이 아니라 `돌솥비빔밥`, `비빔국수`가 아니라 `김치비빔국수`로 읽으면 시드에 없는 메뉴가 되어 만개의 레시피 재료로 판정하고, 그 레시피에는 고추장 속 돼지고기·양념장 속 땅콩이 없어 Safe가 나온다. 한 번 이렇게 저장된 메뉴는 다음부터 DB에서 바로 Safe가 나온다.

- 메뉴판 사진은 지표 대상이 아니지만 같이 쟀다. 시드에 없는 메뉴는 메뉴 하나에 약 2.1초(8개 16.8초)씩 재료를 차례로 찾는다. 처음 보는 메뉴 16개짜리 실제 메뉴판은 판독 22초 + 재료 찾기 30초 이상으로 60초를 넘겼다(같은 메뉴판 두 번째는 22.5초).

## 4. 판정 정확도 (실험 A2)

- 측정일: 2026-10-30 / 측정: Agent, 로컬 docker
- **방법:** 배지를 정해 둔 흐름 E2E 5개를 5회씩 돌린다(`npx playwright test --repeat-each=5`).

| 흐름 | 기대 배지 | 일치 |
| --- | --- | --- |
| `scan-menu-board` (설렁탕) | Avoid | 5/5 |
| `scan-food-photo-single-dish` (설렁탕) | Avoid | 5/5 |
| `diet-toggle-only` (설렁탕) | Avoid | 5/5 |
| `halal-bibimbap-gochujang` (E1) | Check first | **3/5** |
| `peanut-allergy-bibimguksu` (E2) | Check first | 5/5 |

**결과:** 23/25. 목표(25/25)는 달성하지 못했다. "확인된 제한 재료가 있는데 Safe"는 0건이다. 실패 2건은 3절과 같은 원인(판독 이름이 시드와 다름)이다.

- 실험 A1까지 합치면 E1 사진은 15회 중 7회만 Check first였다. E1은 서비스가 풀려는 바로 그 경우라, 할랄 사용자가 비빔밥을 Safe로 안내받는 일이 실제로 일어난다.

## 5. 판정 규칙 표 (실험 B)

- 측정일: 2026-10-30 / 측정: Agent, `POST /api/v1/judgments`에 시드 메뉴 9개
- **결과:** 프리셋 4가지(제한 없음·Halal·Vegetarian·Vegan) × 9칸, 토글 8개 × 9칸, 모두 132칸이 `docs/experiment-plan.md` B1·B2의 기대 배지·규칙과 일치했다.
- 경계 경우(B3):

| ID | 결과 | 기대와 같은가 |
| --- | --- | --- |
| B3-1 `된장찌개`(Halal) | 만개의 레시피 재료 12개(모두 Estimated) → Safe R4, 팝업 없음 | 같음 |
| B3-2 같은 메뉴 다시 | `foods`에 `RECIPE_SEARCH`로 저장되고 같은 결과 | 같음 |
| B3-3 `ㅁㄴㅇㄹ`(Halal) | 만개의 레시피가 상관없는 레시피(계란·표고·간장…)를 돌려줘 Safe R4 | **다름**(기대는 재료 없음 R3) |
| B3-3' `쀍뷁`(Halal) | 재료 없음 → Check R3, "No ingredients were found. Please check before eating." | 같음 |
| B3-4 제한 없음 | Safe R0 | 같음 |
| B3-5 빈 메뉴 이름 `[]`·`[""]`·`[null]`, 수동 입력 `""` | 400 "Please enter a menu name." | 같음 |
| B3-6 저장한 적 없는 사용자 | API 404 "No saved diet settings.", 화면 토글 8개 모두 꺼짐 | 같음 |
| B3-7 같은 `version`으로 동시 저장 2개 / 첫 저장 2개 동시 | 둘 다 200 1개, 409 "Another request was saved first. Please try again." 1개 | 같음 |

- 시드에 없는 메뉴 7개(제육볶음·돈까스·순대국·감바스·불고기·땅콩버터토스트·치즈돈까스)도 넣어 봤다. 레시피 재료가 제한 항목에 맞게 연결됐다(돼지고기·새우·청주·땅콩 등). 다만 재료가 모두 Estimated라서 **Halal 사용자에게 돈까스·제육볶음도 Avoid가 아니라 Check first**다. api.md 규칙(이름 단어·레시피 재료는 모두 `INFERRED`)대로 동작한 결과다.

## 한계

- 확인 시간은 한 사람이 음식 두 개를 3회씩 잰 값이다.
- 포기 횟수는 두 사람에게 지난 한 달을 떠올려 답하게 한 값이다.
- 3~5절은 Agent가 로컬 docker에서 잰 값이다. 배포 환경과 실제 휴대폰에서는 다시 잰다(experiment-plan.md D2·D3).
